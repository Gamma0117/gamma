# P0-6 2차 수정 계획 기술 검토

결론: 계획의 기술 검토는 통과입니다. 지난 다섯 지적과 Neutralize 순서 문제는 수정 계약으로 해결됐습니다. 구현 승인은 사용자의 결정이며, P0-6 구현을 실행하거나 검증한 결과는 아닙니다. 게임 코드는 변경하지 않았습니다.

## 이전 지적의 해결

| 항목 | 수정 계약 | 검토 결과 |
| --- | --- | --- |
| 확인 번호가 남은 입력을 건너뜀 | 수신 최댓값과 확인 번호를 분리. 대기열이 있으면 앞 번호 - 1, 없으면 수신 최댓값 | 대기 입력은 항상 확인 번호보다 큼. 중복·늦은 입력 폐기로 미처리 원본을 확인하지 않음 |
| 반복 재동기화 | 정상 경로는 40개에서 전송·예측을 일시 정지하고 기록 보존. 방어 경로는 고정 boundary까지 확인 대기 | 기록 잘림을 피하고, 공백이 생겨도 재개 조건이 유한함 |
| 단발 입력 무한 대기 | 채우기 대기는 최대 두 틱, 셋째 틱에 하나라도 소비 | 단발 W·점프·중립도 처리·확인됨 |
| 같은 프레임의 Esc 후 재캡처 | takeReleased와 프레임 차단 표시를 유지, 차단 프레임의 Space 탭 폐기 | 시작·끝이 허용이어도 중간 차단이 latch를 지움 |
| epsilon보다 작은 몸체 | 폭·키 최소 0.1, 충돌 상자 축 크기 최소 1/16 | 정수·청크·먼 좌표 경계에서도 후보 범위가 비지 않음 |
| Neutralize가 먼저 도착함 | neutralizedThrough를 저장하고 나중에 받은 해당 범위 입력도 중립으로 처리 | 늦은 입력 판정과 별도로 중립화가 보존됨 |

## 작은 모델의 확인 결과

아래 결과는 수정안의 대기열·번호·상태 전환 규칙을 옮긴 Python 모델의 결과입니다. 아직 작성되지 않은 ServerPlayer, LocalPlayer, MovementSampler나 실제 충돌 물리를 테스트한 것은 아닙니다. 프레임 사건 모델의 시계 계산은 기존 TickScheduler의 마감 시각 규칙과 동일하게 옮겼습니다.

- 입력 1,2,4,3 → 처리 뒤 확인 번호 1,3,4.
- 입력 1,2,2 → 확인 번호 1,2. 중복 2가 원본 2를 먼저 확인하지 않음.
- 입력 1..40과 중복 40 → 최종 네 입력을 처리하며 확인 번호 37,38,39,40.
- 단발 W·점프·중립 → 선택 순서 중립, 중립, 해당 입력, 중립. 세 번째 틱에 확인.
- Neutralize(10) → Input(10, jump) → 해당 입력은 중립으로 처리.
- 클라이언트 70틱 동안 서버를 멈춘 모델 → 기록과 번호는 40에서 멈춤. 서버 재개 후 남은 기록을 보존하며 41부터 재개.
- 서버에 101·102가 남은 재동기화 → 새 입력 없이 두 틱에 boundary 102까지 정리하고 103부터 재개.
- 고정 시드의 수신·중복·번호 공백·중립화 조합 20,000틱 → 확인 번호 단조 증가, 남은 입력은 확인 번호 초과, 확인된 원본은 이후 실행되지 않음.
- 30/60/144fps 각각 50개 서버 위상과 동일 시각의 두 처리 순서, 총 300가지 → 입력 폐기 없음, 모든 입력 한 번 처리, 첫 적용 이후 정상 전송 중 굶은 틱 없음.
- 폭 0.1과 4, 중심 0·±16·±30,000,000 → 칸 후보 범위 비지 않음.
- 같은 프레임 Esc 후 클릭 → 캡처는 복원되지만 이전 latch와 그 프레임의 Space 탭은 폐기.

검증 스크립트: [model.py](second_revision_probes/model.py). 출력: [model.log](second_revision_probes/model.log).

## 구현 시 명시적으로 지킬 사항

이는 추가 계획 수정 요청이 아니라 위 계약을 코드로 옮길 때의 확인 사항입니다.

- neutralizedThrough는 `max(기존 값, through)`로만 증가시키십시오. 작은 through 메시지 때문에 이전 중립화 범위가 줄면 안 됩니다. Neutralize(10), Neutralize(3), Input(10) 순서를 회귀 테스트에 포함하면 됩니다.
- 남은 기록이 없고 확인 번호가 lastSentSeq와 같으면 정상적으로 모두 정리된 상태입니다. 빈 기록 자체를 재동기화 사유로 처리하면 안 됩니다.
- 기록 상한의 입력 멈춤 횟수는 정지 상태로 들어갈 때 한 번 세고, 자리가 난 뒤 다시 가득 차는 경우에 새로 세십시오.
- 실제 ServerPlayer/LocalPlayer/LoopModel 테스트로 모델의 불변식을 확인하고, 충돌·중력·보간 결과는 계획에 적힌 물리 통합 테스트로 별도 확인하십시오.

수치 설명의 작은 정정: ±30,000,000에서 double 간격은 2^-28 ≈ 3.73e-9입니다. 계획의 2^-27은 2^25 지점의 간격으로 한 단계 보수적인 값입니다. epsilon=1e-7과 최소 크기의 결론은 그대로 성립합니다.

검토 범위: 제공된 2차 수정안, 유지되는 1차 수정안, 이전 검토 보고서, b11bcbd의 관련 기술 문서와 TickScheduler/CursorController. 새로운 원격 구현을 가져오거나 전체 빌드를 실행하지 않았습니다.
