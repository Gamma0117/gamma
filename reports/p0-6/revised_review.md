# P0-6 수정 계획 기술 검토

이전 지적의 큰 방향은 반영됐습니다. 서버 틱마다 물리를 한 번 계산하고, 입력이 없을 때 중력을 계속 처리하며, 차단을 클라이언트 틱과 별도로 전달합니다. Space의 포커스 규칙, 예측 기록 상한, TickScheduler 정책, 쓸기와 접촉 경계, 점프 중 자동 오르기 금지, 시험 코스와 스폰 정책도 명시됐습니다.

구현 전에 아래 다섯 경계를 보완하십시오. 이 검토는 계획의 계약을 확인한 것이며 구현 승인이 아닙니다. 게임 구현 코드는 수정하지 않았습니다.

## 1. 확인 번호는 정리된 연속 구간이어야 함

`lastInput`은 단순히 완료·폐기한 seq 중 가장 큰 값이면 안 됩니다. 클라이언트가 그 이하의 기록을 모두 지우므로, 그 이하의 원본 입력이 서버에서 앞으로 적용되지 않는다는 보장이 필요합니다. 수신 최댓값과 확인 번호를 분리하십시오.

예를 들어 입력 1, 2, 4, 3이 순서대로 도착하면 대기열은 [1, 2, 4]이고 3은 늦은 입력으로 버려집니다. 버린 번호 3으로 확인 번호를 올린 뒤 이번 틱에 1을 적용하면, 아직 2가 대기 중인데 클라이언트가 2를 지웁니다. 2의 중복 복사본을 버렸을 때도 대기 중인 원본 2까지 확인하면 안 됩니다.

명세를 다음처럼 정하면 됩니다: `lastInput`은 그 이하가 모두 적용·폐기·영구 생략된 정리 구간의 끝입니다. 틱 상태를 게시할 때 모든 pending.seq > lastInput이어야 합니다. 앞에서 버린 초과 입력은 이 구간을 진행시킬 수 있지만, 늦은 입력이나 중복 복사본 하나를 버리는 것만으로 남아 있는 낮은 번호를 건너뛰면 안 됩니다.

테스트: [1,2,4,3], [1,2,2], 40개 입력과 아직 대기 중인 마지막 입력의 중복을 넣고, 게시한 확인 번호 이하의 원본 입력이 이후 틱에서 실행되지 않는지 확인하십시오. 스폰 전 메시지 폐기는 스폰 뒤 수신 번호와 확인 번호를 오염시키지 않아야 합니다.

## 2. 재동기화는 새 입력을 재개하는 조건이 필요함

기록을 비운 뒤 번호를 계속 증가시키며 즉시 새 입력을 보내면 재동기화를 반복할 수 있습니다. 서버에 101·102가 남은 상태에서 클라이언트가 기록을 비웠다고 해 보겠습니다. 새 103을 기록한 뒤 서버 확인 101이 오면 첫 기록 103은 확인 번호 + 1인 102가 아닙니다. 또 비우고 104를 만들면 다음 확인 102에도 같은 공백이 생깁니다. 양쪽이 20Hz로 진행하면 차이가 유지됩니다.

재동기화의 진입·대기·종료 규칙을 정하십시오. P0에서는 진입 당시 마지막 전송 번호를 경계로 저장하고, 그 범위가 서버에서 모두 정리될 때까지 새 번호 입력과 예측을 잠시 멈추는 방식이 가능합니다. 대기 중에는 최신 권한 상태를 반영하고 서버 중력은 계속됩니다. 경계가 확인된 뒤 단조 증가 번호를 유지하며 클라이언트 시계·보간을 초기화하고 재개하면 됩니다. 기존 중립화 메시지로 대기 의도를 중립화할 수도 있습니다.

서버와 함께 입력 세대를 바꾸는 다른 방식도 가능하지만, 클라이언트만 seq를 낮춰 재사용하면 수신 최댓값 검사에 걸립니다. 선택한 방식과 종료 조건을 명시하십시오.

테스트: 대기 입력이 남은 상태에서 기록을 자른 뒤 재동기화하고, 기록 공백이 없는 예측으로 돌아오는지 확인하십시오. 같은 사유로 resyncs가 매 틱 증가하지 않아야 합니다.

## 3. 두 입력이 모이기 전 기다리는 규칙에는 유한한 대기가 필요함

처음 또는 대기열이 빈 뒤 입력 하나만 도착하면, 현재 채우기 규칙은 두 번째 입력을 계속 기다립니다. 단발 W·점프는 적용되지 않고 확인되지도 않습니다. 검토용 모델에서도 서버 10틱 뒤 `pending=[1], ack=0, applied=[]`였습니다. 초안의 "W를 한 번만 보내면 한 걸음 적용" 테스트와 모순됩니다.

두 입력을 모으는 완충 정책은 유지할 수 있습니다. 다만 첫 대기 입력이 일정 서버 틱/시간을 기다리면 하나라도 소비하는 규칙을 넣으십시오. 정상 30/60/144fps 흐름에서 원하는 완충 효과와, 전송이 끝난 부분 대기열의 진행을 함께 검증해야 합니다.

테스트: 단발 W, 단발 점프, 빈 대기열에 마지막 중립 입력 하나만 남는 경우, Neutralize 뒤 입력 하나만 남는 경우. 중력은 계속 계산하고 해당 번호는 유한한 시간 안에 확인돼야 합니다.

## 4. A/B 두 끝점만으로는 같은 프레임의 차단을 감지하지 못함

현재 handleInput은 Esc로 캡처를 해제한 뒤 같은 poll의 클릭으로 다시 캡처할 수 있습니다. 프레임 시작 A와 끝 B만 보면 둘 다 허용이지만 중간에 차단이 있었습니다. 이전 latch와 Space 눌림이 남을 수 있습니다.

기준 코드의 실제 CursorController와 InputState를 사용한 결과:

```
allowed_A=1 after_Esc=0 allowed_B=1 block_seen_by_endpoints=0 old_space=1
```

Esc 등 차단 동작 자체에서 초기화·중립화를 호출하거나, 해당 프레임에 차단이 한 번이라도 있었음을 보존하십시오. 같은 프레임에서 다시 허용돼도 이전 latch는 복구하면 안 됩니다. 눌림 기억 조건도 A && B만이 아니라 프레임 내부의 차단을 고려해야 합니다.

테스트: 이미 캡처한 상태에서 Space 탭 → Esc → 새 클릭을 같은 poll에 넣습니다. 최종 캡처가 true여도 옛 점프는 없어야 하고 Neutralize가 나가야 합니다. Space 탭은 해제돼 있고 isKeyDown은 false인 조건으로 검사해, 다시 잡은 뒤 계속 누르는 키 정책과 구분하십시오.

## 5. 플레이어 폭·키의 하한은 epsilon과 맞아야 함

폭과 키 (0,4]는 epsilon보다 작은 상자도 허용합니다. 폭 1e-8, 중심 x=16, epsilon=1e-7이면 제안한 칸 범위가 다음처럼 비어 버립니다.

```
first = floor(min + epsilon) = 16
last  = ceil(max - epsilon) - 1 = 15
```

이때 Y 쓸기에서도 X 후보 범위가 비어 바닥을 검사하지 못할 수 있습니다. 플레이어 폭·키에는 epsilon보다 충분히 큰 양의 하한을 두거나, 작은 상자에서도 칸 조회가 정의되는 방식을 정하십시오. 실제 게임 수치와 좌표 정밀도에 맞는 하한을 선택하고 JSON 범위 테스트를 추가하면 충분합니다.
