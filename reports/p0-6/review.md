# P0-6 계획 기술 검토

대상은 붙여 주신 P0-6 초안과 기준 코드 `b11bcbd`입니다. 구현 코드는 수정하지 않았습니다. 아래 의견은 구현 승인이 아닙니다.

선택 사항 1~4의 추천 방향은 타당합니다. 부분 블록의 화면 렌더링은 미루고 물리 상자 목록으로 자동 오르기를 검증하는 것, JSON 시험 코스를 두는 것, EnTT를 미루는 것, 자유 비행을 F3 체크박스로 전환하는 것에 찬성합니다. 다만 서버 물리 시간과 입력 계약은 구현 전에 수정 계획을 다시 정해야 합니다.

## 1. [P1] 물리 시간은 입력 개수가 아니라 서버 틱으로 진행

초안은 서버 한 틱에 쌓인 입력을 모두 처리하고, 입력 하나마다 50ms의 물리를 실행합니다. 따라서 40개가 도착하면 서버 한 틱에 2초의 물리가 진행됩니다. 반대로 입력이 없으면 중력까지 멈춰, 최소화한 플레이어가 공중에서 정지합니다. 월드·다른 개체는 계속 20Hz로 도는데 플레이어만 클라이언트 전송량에 따라 시간이 흐르게 됩니다.

기존 `22_p0_tech.md`는 서버가 20Hz의 권한 시뮬레이션을 맡도록 정했습니다. 플레이어도 실행한 서버 틱마다 고정 dt로 한 번 계산하십시오. 서버의 정상 catch-up은 실행하는 서버 틱마다 한 걸음씩 진행하면 됩니다. 입력이 없는 틱에는 중립 의도를 적용해 이전 W·점프 의도를 반복하지 않되, 중력과 충돌은 계속 계산해야 합니다. 청크 미로드 때문에 명시적으로 frozen인 경우는 별도입니다.

입력의 도착·정렬·확인 처리와 물리 진행을 분리하고, 한 서버 틱에 사용할 입력을 고르는 규칙과 늦거나 초과된 입력을 버리는 규칙을 정하십시오. 여러 입력을 받았다는 이유로 서버 시간을 추가로 진행하면 안 됩니다. PlayerState에는 `serverTick`도 필요합니다. 중립 물리는 lastInput이 같아도 진행되므로, 입력 확인 번호만으로 상태의 시각을 표현할 수 없습니다.

검증에 다음을 넣으십시오.

- 입력 40개가 한 번에 와도 물리 시간이 실행한 서버 틱 수 × 50ms를 넘지 않음.
- 공중에서 입력이 끊겨도 중력·착지는 계속됨.
- 동일한 논리 입력을 30/60/144fps에서 전달해도 서버 물리 시간이 같음.
- 입력을 전혀 받지 않는 틱에 이전 W·점프 의도가 다시 적용되지 않음.

## 2. [P2] 입력 차단과 점프 기억의 수명

최소화 분기에서는 클라이언트 틱이 돌지 않습니다. 틱에서만 중립 입력을 만든다면 포커스 상실 직후 중립화가 서버로 전달되지 않고, 이미 대기 중인 W·점프 입력도 남습니다. "이전 입력을 되풀이하지 않는다"는 규칙은 대기 중인 옛 입력을 무효화하지 않습니다.

포커스 상실·캡처 해제·UI 입력 전환·자유 비행 전환 등 입력을 받지 않는 상태가 되면, 클라이언트 틱과 별도로 서버에 입력 차단/중립화를 전달하고 그 이전에 대기하던 의도를 무효화하는 정책을 정하십시오. 입력 유효 세대나 우편함 초기화 같은 단순한 방식으로 처리할 수 있습니다. 이후 서버 물리는 1번의 중립 의도로 계속 진행합니다. 관성의 감속 여부는 movement.json의 정한 규칙을 따릅니다.

점프 latch는 포커스 상실 때뿐 아니라 입력 허용 조건이 true에서 false로 바뀔 때 지우십시오. 예를 들어 틱 사이 Space 탭 → Esc → 다시 캡처가 일어나도 예전 탭이 다음 틱으로 넘어가면 안 됩니다.

또한 현재 InputState는 포커스 상실 때 마우스 버튼 표시만 지웁니다. 실제 기준 코드로 다음을 확인했습니다.

```
Space 눌림 → 포커스 상실 → 복원 → 새 클릭 → takeFocusLost()
focus_loss_consumed=1 old_space_press=1 new_focused_click=1
```

sampler를 초기화해도 같은 프레임에서 `wasKeyPressed(Space)`를 다시 읽으면 옛 점프가 재주입됩니다. 입력 기록 단계에서도 포커스 상실 이전의 게임 키 눌림을 무효화하고, 비포커스 키 눌림을 받지 않도록 하십시오. 복원 후의 새 Space는 정상적으로 받아야 합니다. P0-5에서 고친 클릭 순서와 같은 테스트를 Space에도 적용하면 됩니다.

자료: [검토용 코드](current_contract_probe.cpp), [출력](current_contract_probe.log).

## 3. [P2] 예측 기록·확인 번호·보간 규칙

입력 sequence가 전송 순서인지 논리 시뮬레이션 틱인지, 서버가 버린 입력을 어떤 확인 번호로 알리는지, 클라이언트가 버린 틱의 번호와 상태를 어떻게 재동기화하는지 정하십시오. 이는 1번의 서버 시간 규칙과 함께 바뀌어야 합니다. 물리 없이 확인한 frozen 입력과 폐기한 입력도 기록 정리가 가능해야 합니다.

서버 입력 대기열 40개 제한은 클라이언트의 예측 기록을 제한하지 않습니다. 기록 상한과 초과 시 재동기화 정책을 명시하십시오. 서버 상태가 오지 않는 동안 기록과 재실행 비용이 계속 커지지 않아야 합니다. 오래된 권한 상태가 이미 지운 기록보다 앞설 때의 처리도 필요합니다.

카메라 보간은 다음과 같이 명확히 적으면 됩니다.

```
alpha = clamp(1 - (nextTickTime - now) / tickInterval, 0, 1)
```

서버 보정을 순간이동으로 처리한다면 보정·재실행한 결과로 이전/현재 보간 상태를 함께 초기화해야 합니다. 최초 스폰에도 적용합니다. 이전 예측 위치와 새 위치가 보간 쌍에 남으면 순간이동 정책과 다르게 화면이 끌리거나 되돌아갑니다.

현재 TickScheduler는 상한을 넘으면 상한 개수가 아니라 1틱만 실행하고 나머지를 버립니다. 상한 5에서 6틱이 밀린 실제 결과는 `run=1, skipped=5`였습니다. 클라이언트에서 이 정책을 그대로 쓸지, 5틱을 실행하고 초과분을 버릴지 정하십시오. 서버의 기존 정책을 함께 바꿀 필요는 없습니다.

"같은 월드면 보정 0"은 동일한 논리 틱에 같은 입력을 적용한 통제된 테스트에서 확인하십시오. 실제 서버 스레드·독립 클라이언트 시계·비동기 청크 전달을 쓰는 통합 테스트는 같은 틱의 상태 일치와 권한 상태로의 수렴을 검증하는 것이 맞습니다. 입력이 서버 틱에 늦게 도착한 경우까지 보정 0을 요구하면 시간 의존 테스트가 됩니다. 비트 단위 동일성도 같은 플랫폼·빌드·부동소수점 환경에서의 보장으로 한정하십시오.

## 4. [P2] 쓸기 충돌과 자동 오르기 경계

최대 낙하 속도 78에서 한 틱 이동은 3.9블록입니다. 최종 위치의 상자만 검사하면 1블록 바닥을 통과할 수 있습니다. 전체 이동 구간의 블록과 상자를 대상으로 축별 이동을 제한한다는 계약을 명시하고, 최대 속도로 얇은 바닥·천장·벽을 통과하지 않는 테스트를 넣으십시오.

미로드 규칙 A/B는 좋습니다. 다만 B의 "걸친 청크"는 양의 부피로 겹치는 경우여야 합니다. 로드된 청크의 동쪽 끝 x=16에 몸이 닿았을 뿐인데 미로드 이웃을 포함하면, A로 막힌 다음 틱부터 B로 frozen되어 뒤로도 못 갑니다. 정확히 접한 경계에서 뒤로 물러나는 테스트, 실제로 경계를 걸친 경우 frozen 테스트, 음수 좌표 대조군을 함께 넣으십시오. 경계와 겹침의 epsilon 규칙을 하나로 정해야 합니다.

자동 오르기의 "이전에 땅에 있었음" 조건은 점프를 시작한 틱에도 참입니다. 상승 중인 점프를 step-down 결과로 바꿔 점프를 취소하지 않도록, 점프 시작/상승 시 자동 오르기와의 우선순위를 정하십시오. 공중 테스트 외에 발사 직후 반블록 앞에 있는 경우를 넣으면 됩니다.

추가 계약은 간단히 명시하면 충분합니다: collision shape의 로컬 범위·유한성·min/max, 선택한 step 경로에 따른 속도와 접지 갱신, movement.json 수치의 유한성과 범위. 플레이어 폭을 JSON으로 바꿀 수 있다면 "최대 4개 청크" 가정이 성립하는 상한을 두거나 실제 겹친 청크를 모두 계산하십시오.

제안된 점프 계산 순서 자체는 맞습니다. dt=0.05, vy=9.8에서 먼저 중력 32를 적용하는 이산 계산의 꼭대기는 1.26블록으로, 목표 1.2~1.3 범위입니다.

## 5. 시험 코스와 검증 범위

flat.json의 boxes 확장은 가능합니다. 적용 순서(층 생성 후 JSON 순서대로, 뒤 항목이 이김), 정수 좌표와 y 범위, from≤to, 엄격한 상태 문자열 해석을 정하십시오. 청크와의 교집합만 생성하고, 끝 좌표의 +1·구간 길이는 넓은 정수로 계산해야 합니다. air로 파낸 뒤를 포함해 마지막에 높이맵을 다시 계산하십시오. 청크 경계·음수 좌표·겹친 boxes·air 삭제·잘못된 범위 테스트가 필요합니다.

초기 스폰 완료 전에는 spawnColumn 둘레를 로드하도록 유지하십시오. 자유 비행 override가 스폰 청크를 먼저 내려 영원히 스폰을 기다리는 순서가 생기지 않아야 합니다. 시험 코스의 실제 스폰 상자와 머리 공간도 확보하십시오.

현재 스크린샷 검사기는 화면 위 10%의 하늘 95%와 지형 영역의 초록색 80%를 요구합니다. 눈 높이와 시험 코스를 바꾸면 이 기대 장면도 달라집니다. 통제된 스크린샷 장면을 정하거나 검사 기준을 새 장면에 맞추되, 그리기를 끈 음성 대조군이 앱 성공·새 PNG·검사기 종료 코드 2를 확인하는 계약은 유지하십시오.

부분 블록 화면 구현을 미루는 만큼, 자동 오르기는 실제 블록 조회 adapter를 거친 CPU 통합 테스트까지 확인하고 README/ROADMAP에 화면 확인 범위를 명시하면 됩니다. P0-6에서 정점 형식을 다시 열 필요는 없습니다.

## 검토 범위

기획서의 조작·서버 권한·고정 틱, 현재 서버/월드/클라이언트 API, 입력 상태와 TickScheduler, 평지 생성과 스크린샷 검사기를 대조했습니다. 기준 코드에 대한 작은 계약 확인 프로그램과 점프 수치 계산만 실행했습니다. P0-6 구현이나 빌드 결과를 검증한 것은 아닙니다. 원래 체크아웃은 변경하지 않았습니다.
