# P0 기술 설계

P0의 목표는 렌더거리 16청크에서 60fps로 걸으며 블록을 부수고 놓고, 저장·불러오기가 되고, 싱글도 내장 서버로 도는 엔진이다. 이 문서는 Claude Code가 코딩을 시작하기 위한 기준이며, 세부 구현은 작업 중 조정한다.

**가정한 목표 사양**: GTX 1060급 GPU, 4코어 CPU, RAM 8GB, Windows 10+/Linux (최소 사양은 아직 미확정).

## 구조

클라이언트(보여주기·입력)와 서버(게임 규칙·월드)를 처음부터 나눈다. 싱글은 같은 프로그램 안에서 서버를 띄우고 메모리로 직접 연결하고, 멀티는 같은 패킷을 네트워크로 보낸다.

```
[클라이언트 스레드]  입력 · 렌더 · UI · 예측/보간
        │  패킷 (싱글: 메모리 루프백 / 멀티: ENet)
        ▼
[서버 스레드 20tps]  월드 권한 · 개체 · 규칙 · 명령어
        │  작업 요청 / 결과
        ▼
[워커 스레드 N개]    지형 생성 · 메싱 · 조명 · 경로 탐색 · 압축·파일 입출력
공통 기반: core(로그·잡·프로파일러) · data(JSON 레지스트리) · platform(창·입력·파일)
```

월드를 바꾸는 것은 서버뿐이고, 무거운 계산은 워커에 맡긴다.

| 모듈 | 하는 일 |
| --- | --- |
| core | 로그, 수학, 잡 시스템(작업 분배), 프로파일러, 이벤트 |
| platform | 창·입력(GLFW), 파일, 시간 |
| data | JSON 로더, 레지스트리(블록·아이템 ID), 스키마 검사, 번역 |
| world | 블록, 청크, 월드, 지형 생성, 조명, 저장 |
| entity | ECS(EnTT) 컴포넌트: 위치, 물리, 체력, 인벤토리, 애니메이션 |
| net | 패킷 정의·직렬화, 연결(내장 루프백 / ENet) |
| server | 틱 루프, 월드 권한, 플레이어 세션, 명령어 |
| client | 월드 사본, 내 이동 예측, 다른 개체 보간, 카메라 |
| render | OpenGL 4.5, 청크 메싱, 텍스처 배열, 쉐이더(핫 리로드), 그림자·안개·물·후처리 |
| ui | 디버그(Dear ImGui), 최소 HUD |
| sim | P2부터: 왕국·주민·경제 (P0에서는 빈 틀만) |
| tools / tests | 텍스처 생성기, 벤치마크, 단위 테스트 |

## 스레드

| 스레드 | 역할 |
| --- | --- |
| 메인 (클라이언트) | 입력, 렌더 명령, UI, 메시 업로드 |
| 서버 | 초당 20틱 고정 루프: 월드·개체·규칙 |
| 워커 (코어 수 − 2개) | 지형 생성, 메싱, 조명, 경로 탐색, 압축·파일 입출력 |
| 네트워크 | 패킷 송수신 (멀티만) |

월드 데이터는 서버 스레드만 쓴다. 워커는 청크 복사본이나 새 청크를 만들어 결과만 돌려준다(락을 최소화).

## 핵심 데이터 구조

- **좌표**: 블록 좌표는 32비트 정수(±3천만 충분), 개체 위치는 double, 렌더링은 카메라 기준 상대 좌표(float)로 멀리서도 떨림 없음.
- **높이**: 내부적으로 y −64\~320(16층 섹션 24개). 게임 규칙으로 −50 기반암, 300 건축 한계를 강제.
- **블록 상태**: 16비트 ID (방향·성장 단계 포함 최대 65,536개).
- **섹션 (16³)**: 팔레트 + 비트 패킹 배열, 하늘빛·블록빛 각 4비트. 전부 공기면 저장하지 않음.
- **청크**: 섹션 24개 + 높이맵 + 바이옴 + 상태(생성 중 / 조명 완료 / 활성).

## 지형 생성 단계

1. 높이: 대륙·침식·봉우리 3가지 노이즈를 섞어 지표 높이
2. 기후: 온도·습도·마력 노이즈 → 바이옴 11종
3. 표면: 바이옴별 윗층 블록(풀·모래·눈 등)
4. 동굴: 3D 노이즈(넓은 동굴 + 길은 터널)
5. 광맥: 깊이·바이옴 보정 (데이터 파일의 generation 값)
6. 장식: 나무·풀·꽃 (구조물은 P1부터)

같은 시드와 청크 좌표면 언제나 같은 결과(순서 무관)여야 하며, 테스트로 검사한다.

## 렌더링

- **메싱**: 섹션마다 같은 면을 합치는 그리디 메싱, 꼭짓점마다 주변 블록으로 계산한 그늘(AO). 불투명·반투명 메시를 따로. 블록이 바뀌면 가까운 섹션부터 다시 만든다.
- **그리기**: 텍스처 배열 하나 + 멀티드로 인디렉트로 수천 섹션을 드로우콜 몇 번에. 절두체 컬링 + 섹션 가시성 그래프 기반 오클루전 컬링.
- **순서**: 그림자(CSM) → 불투명 → 하늘 → 반투명·물 → 안개 → 블룸·톤매핑 → UI.

## 물리·조명

- 플레이어 충돌: 상자(AABB) vs 블록 격자, 0.6블록 계단 자동 오르기, 중력 32블록/초², 최대 낙하 속도 78블록/초 (마인크래프트와 비슷한 느낌).
- 조명: 하늘빛·블록빛 0\~15를 넓이 우선 탐색으로 퍼뜨림, 청크 경계는 대기열로 이어 처리.

## 네트워크

서버가 권한을 갖고, 클라이언트는 자기 이동만 미리 예측한 뒤 서버 결과로 보정한다. 다른 개체는 100ms 뒤의 모습을 보간해 부드럽게 보여준다.

| 패킷 | 방향 | 내용 |
| --- | --- | --- |
| Handshake / Login | 양방향 | 버전 확인, 플레이어 식별 |
| ChunkData | 서버 → | LZ4 압축 섹션 묶음 |
| BlockChange / MultiBlockChange | 서버 → | 블록 변경 |
| PlayerInput | → 서버 | 이동 키, 시선, 행동 (틱 번호 포함) |
| PlayerState | 서버 → | 예측 보정용 위치·속도 |
| EntitySpawn / Move / Remove | 서버 → | 다른 개체 |
| DigAction / PlaceAction | → 서버 | 부수기 시작·취소·완료, 놓기 |
| Chat / Command | 양방향 | 채팅·명령어 |
| TimeUpdate / KeepAlive | 서버 → | 시간, 연결 유지 |

## 성능·메모리 예산

| 프레임 (60fps = 16.6ms) | 예산 | 서버 틱 (20tps = 50ms) | 예산 |
| --- | --- | --- | --- |
| 렌더 명령 | 6ms | 청크 틱(액체·작물) | 8ms |
| 메시 업로드 | 1.5ms | 개체·물리 | 10ms |
| 개체 보간·애니메이션 | 3ms | 주민 AI (P2부터, 나눠서 처리) | 12ms |
| UI | 1ms | 왕국 시뮬레이션 (P2부터) | 5ms |
| 입력·예측 | 0.5ms | 네트워크 | 3ms |
| 여유 | 4.6ms | 여유 | 12ms |

- **메모리**: 섹션 하나 약 8KB, 렌더거리 16청크면 약 1,100청크 × 비어있지 않은 섹션 약 12개 ≈ 110MB. 메시는 GPU 메모리 약 300MB 이하 목표.
- **청크 생성 속도**: 워커 2개로 초당 100청크 이상 (달리며 탐험해도 빈 곳이 안 보이게).

## 저장

영역 파일(청크 32×32) + 4KB 단위 공간 + LZ4 압축. 저장은 워커에서 비동기로 하고, 5분마다 자동 저장. 자세한 파일 구성은 데이터 파일 구조 탭.

## 라이브러리·도구

CMake + vcpkg 로 관리: GLFW, glad, GLM, stb\_image, EnTT, FastNoiseLite, nlohmann/json, LZ4, ENet, Dear ImGui, Tracy(프로파일러), Catch2(테스트). 오디오(miniaudio)·물리(Jolt)는 P1 이후.

## 테스트

- 지형 생성 결정성: 같은 시드·좌표 → 같은 청크 해시
- 저장 왕복: 저장 후 불러오면 똑같은 데이터
- 패킷 직렬화 왕복
- 메셔: 알려진 모양의 면 개수 검사
- 성능 벤치마크: 청크 1,000개 생성·메싱 시간을 매 빌드 기록
